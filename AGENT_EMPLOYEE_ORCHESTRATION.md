# Режим разработки: сеньор и модель-исполнитель

Включён по прямому поручению пользователя 15 сентября 2026 года.
Это организация работы Codex над репозиторием, **не** изменение runtime
производственного агента Светы и не снятие его approval gates.

## Механизм

Главный агент использует штатные средства создания подагента, передачи задания,
получения результата и отправки замечаний. Отдельный демон, API-ключ или платный
внешний сервис для этого режима не создаются. Делегирование выполняется во время
активной сессии; этот файл сам по себе не запускает работу после её завершения.
Продолжение в следующей сессии восстанавливается по карточкам, Git и отчётам.

Документация механизма: [OpenAI Docs: Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents).
Доступность моделей определяется инструментами текущей сессии, не названием
в этом файле. Общий расход токенов может вырасти; цель — уменьшить долю работы
дорогой модели. Фактическую экономию нельзя объявлять без данных учёта.

## Роли

| Роль | Исполнитель | Обязанности |
|---|---|---|
| Сеньор | Главная модель сессии | Контракт, границы задачи, независимый review, приёмка |
| Исполнитель | `gpt-5.6-luna`, high для кода с edge cases | Реализация одной карточки, локальные тесты, исправления |
| Эскалация | `gpt-5.6-terra`, high, если доступна | Только узкая задача, которую не решил первый исполнитель |
| Выпуск | Главный агент | Проверки принятого diff, сборка, health, scoped commit |

Это настроенный выбор для текущего инструментария, не утверждение о тарифах
или превосходстве моделей. Если выбранная модель недоступна, сеньор сообщает это
и выбирает доступного исполнителя из разрешённого пользователем класса;
не наследует дорогую модель молча. Для совсем механических задач effort можно
уменьшить; security review всегда остаётся независимым.

## Рабочий цикл

1. Сеньор читает `git status`, карточку и её зависимости, устанавливает исходный
   commit и WIP. Выбирает одну ограниченную задачу из playbook.
2. Создаёт подагента с `fork_turns=none`, явно заданной моделью и коротким пакетом:
   карточка, пути, контракт, тесты, запрещённые изменения, формат ответа.
   Не копирует всю историю и полный roadmap в каждый запрос.
3. Исполнитель меняет только закреплённые файлы, проверяет тестами, возвращает
   пути/команды/числа passed-failed-skipped/ограничения. Сам не делает deploy,
   commit, push и не запускает ещё агентов.
4. Сеньор в это время готовит независимые критерии приёмки, проверяет соседнюю
   границу или актуализирует координационные документы. Не дублирует реализацию.
5. Сеньор читает **реальный diff и тесты**, проверяет callers, отрицательные пути,
   транзакции и права. Отчёт исполнителя не заменяет эту проверку.
6. Замечания отправляются тому же исполнителю: воспроизводимый дефект, ожидаемое
   поведение и требуемый regression test. Не выдаётся новая широкая задача.
7. После максимум двух циклов исправлений нерешённый вопрос сужается и передаётся
   более сильному исполнителю либо разбирается сеньором. Бесконечного автоповтора нет.
8. После приёмки выполняются профильные проверки и production-процедура,
   создаётся отчёт, обновляется статус карточки, делается scoped commit.
9. Если активное поручение включает продолжение плана, следующую доступную карточку
   сеньор назначает сам. Обычные передачи и исправления не требуют участия человека.

## Конкурентность и общее дерево

- По умолчанию один пишущий исполнитель. Ещё один допустим только для независимой
  области с непересекающимися файлами и когда это действительно сокращает работу.
- Главный агент не редактирует закреплённые production-файлы до сдачи исполнителем.
- Общая рабочая копия — не изоляция. Перед форматированием, сборкой и commit
  убедиться, что другие исполнители прекратили правки соответствующих файлов.
- Проверочные тесты можно делегировать отдельно только при независимом объёме;
  не плодить агента на каждый `rg` или одну shell-команду.

## Приёмка и ограничения полномочий

- Сеньор может закрывать технические review gates playbook независимой проверкой;
  это не разрешение на миграцию реальных данных, новые расходы или внешние действия.
- Подагент не может править approval/RBAC/ACL/lease/budget или тесты так, чтобы
  скрыть дефект. Пропуск/ослабление теста требует отдельного обоснования сеньору.
- При ошибке инструментов, отсутствующем доступе или запрещённом действии
  исполнитель сообщает сеньору. Сеньор не обходит системный запрет.
- Существующий запрет push всей накопленной истории с CAD-коммитами сохраняется.
- Результат работы не означает результат релиза. Каждый отчёт различает
  TESTED, REVIEWED, DEPLOYED и ограничения проверки.
- Ни автоматический перезапуск сессии, ни гарантированное продолжение после
  исчерпания лимитов этим режимом не реализованы.

## Короткое задание исполнителю

```text
Ты исполнитель, сеньор — root. Выполни только E__ в указанном репозитории.
Прочитай AGENTS.md, нужную карточку и применимые правила playbook.
Разрешённые файлы: <список>. Исходный commit/WIP: <описание>.
Контракт: <точные условия>. Обязательные негативные тесты: <список>.
Не меняй остальное; не commit/push/deploy; не создавай подагентов.
Используй apply_patch. Запускай тесты только на отдельной тестовой БД.
Верни кратко изменения, команды и результаты, найденные ограничения.
При блокировке сообщи root, не придумывай обход.
```

## Учёт работы

Отчёты: `docs/agent-employee-delivery/E__-<slug>.md` по форме playbook.
Дополнительно указать модель исполнителя, число циклов review, замечания сеньора
и чем они закрыты. Если счётчики usage недоступны, записать «экономия не измерена»;
не оценивать проценты по длине ответа или количеству файлов.

Первый контрольный прогон режима — E00, read-only сверка AgentTask по квитанции.
Готовность определяется отчётом E00, не самим наличием этого документа.
