# EMAIL_SUBSYSTEM_PLAN — почтовая подсистема: от «зеркала» к рабочему клиенту с автономным агентом

## Контекст

Проведён сквозной аудит почтовой подсистемы (ингест IMAP → домен → API → веб-клиент → настройки → агентский путь → мобильное приложение). Подсистема формально «сделана» — ~11.5 тыс. строк, 74 теста, OAuth2, пресеты провайдеров, адресная книга, подписи, правила, шаблоны — но при проверке кода обнаружились дефекты четырёх классов:

1. **Дыры доступа.** Приватность личных ящиков (`backend/app/domain/email_access.py`) полностью обходится через surface черновиков: пять эндпоинтов `/api/email/drafts*` не проверяют владельца вообще — любой пользователь читает чужие черновики, правит их и отправляет письма от чужого имени. Правила фильтрации выбираются без учёта `owner_sub`, поэтому правило рядового сотрудника применяется ко всем ящикам компании. Вложения отдаются с `Content-Disposition: inline` — присланный HTML/SVG исполняется в контексте сессии.

2. **Молчаливые потери данных.** Парсер не читает `References`/`Reply-To`/`Auto-Submitted`/`Authentication-Results` и не делает HTML→text фолбэк, а HTML-only писем — большинство: у них пустой `body_text`, они не находятся поиском, не матчатся правилами, приходят агенту «пустыми». Пересылка молча теряет вложения (`forward_of_message_id` не передаётся фронтом и не читается отправителем). Действия правил `forward_to`/`assign_role` заявлены и не реализованы (`assign_role` — буквально `msg.mailbox = msg.mailbox`). Три `email.templates.*` разрешены агенту в `gateway.yml` и отсутствуют в диспетчере.

3. **Клиент не является почтовым клиентом.** Состояние никогда не пишется обратно на IMAP: архив/прочитано/удаление живут только в Postgres, обратно с сервера не читаются, синкается одна папка. Нет пагинации, нет папки «Черновики» (сохранённый черновик исчезает навсегда), нет автосохранения, нет undo, iframe письма фиксирован в 360 px со светлым текстом на прозрачном фоне.

4. **Автоматизм разорван в самом главном месте.** `_store_attachment` создаёт `Document` из вложения — и **не ставит задачу распознавания**. `process_document` вызывается только из правила `run_extraction`, ручного API или `run_triage`, которого нет в beat-расписании. То есть «счёт пришёл письмом → распознался → появился в системе» сейчас не работает вовсе, хотя docstring `api/email.py:1575` утверждает обратное. При этом `auto_supplier_task` (`tasks/extraction.py:2161`) — готовая 5-ступенчатая логика сопоставления поставщика (ИНН → email → телефон → LLM по имени → создание) — написана и **не вызывается ниоткуда**, а YAML-сценарии `email-triage.yml` / `draft-email.yml` полностью написаны, зарегистрированы с cron-триггером в `gateway.yml` и никогда не исполняются, потому что планировщика сценариев не существует.

**Решения пользователя, зафиксированные до начала работ:**
- IMAP — **полный двусторонний синк** (флаги + папки + IDLE), а не зеркало.
- Автономия агента — **авто до Needs Review**: агент классифицирует письмо, распознаёт вложения, создаёт Invoice/Document, привязывает поставщика, уведомляет ответственного; approve остаётся за человеком.
- Авто-утверждение счетов из почты — **настройка per-mailbox, по умолчанию выключена** (глобальный `auto_verify` для ручной загрузки не трогаем).
- Мобильная навигация — **объединённые «Входящие»**: письма, документы на рассмотрении и аномалии в одной ленте дел.
- Порядок — **фазами, безопасность первой**. Ничего полезного не вырезаем: недоделанное доделываем или переделываем.

Целевой результат: почта, которой можно пользоваться как основной (в том числе с телефона), и «Света», которая реально разбирает входящий поток, объясняя каждое своё действие.
