# E21.3d — Учёт активного времени

Дата: 6 октября 2026. Исполнитель и приёмка: Claude Code (root).

До среза измерение `active_seconds` (по умолчанию 2 часа) было объявлено в
ledger, но не резервировалось и не списывалось.

## Контракт

`execute_claimed_step` стал обёрткой над прежним исполнителем:

- до исполнения резервируется `min(потолок шага, остаток бюджета)`, где
  потолок = `min(step.timeout_seconds, 700)`: Celery-задача исполнения шага
  жёстко ограничена `time_limit=700`, дольше шаг физически не живёт;
- остатка нет → шаг не запускается: попытка и шаг `failed`, заказ `blocked`
  с `active_time_budget_exceeded`;
- после исполнения списывается фактическое время, даже если оно больше
  резерва: ledger фиксирует перерасход (`budget_actual_overrun` /
  `budget_charge_exceeded`), и следующий шаг уже не зарезервирует время;
- падение worker'а оставляет резерв неснятым — он учитывается целиком;
- повторная доставка той же попытки делит одну резервацию; закрывает её
  только создатель;
- ожидание человека в активное время не входит: шаг у approval-gate
  останавливается за секунды, продолжение — новая попытка со своим резервом.

**Граница — на уровне шага.** Шаг, начатый в пределах бюджета, может
перерасходовать его не больше своего потолка; принудительной отмены уже
идущего шага по бюджету нет (отмена посреди хода агента оставила бы эффект
инструмента неизвестным). Detached planner/verifier вне шагов в активное время
не входят; их вызовы модели учитываются в `llm_calls`.

## Тесты

`tests/test_work_budget_active_time.py`: резерв = потолок 700 при таймауте 900
и списание измеренного времени; исчерпанный бюджет блокирует до запуска
исполнителя; резерв не больше остатка (60 при бюджете 60).
`test_work_budget_headless.py`: «ни одной резервации» уточнено до «ни одной
резервации отправки», резерв времени закрыт.

Регрессия: набор падений work orders/planning совпадает с базовой линией;
planner 23, verifier 17, ledger/lease/corpus 57, бюджетные профили 105,
`tests/ai` 3736 — passed.
