# E26 — Контракт ScriptRun и модель угроз (ADR)

Дата: 10 октября 2026. Автор и приёмка: Claude Code (root).
Статус: принят как основа E27. Открытое решение владельца — gVisor (ниже).

## Контекст

Агенту нужен одноразовый код (пересчёт, разбор файла, преобразование данных)
без превращения backend в исполнитель произвольного Python. Старый
`skill-runner` выведен из работы и ничего не исполняет (410). Модель
`AgentScriptRun` хранит код и статус, но исполнителя нет. AST-проверки,
таймауты и `subprocess` внутри backend песочницей не считаются: у процесса
backend есть сеть, секреты, БД и вся файловая система приложения.

## Решение

**Один запуск — один свежий контейнер**, создаваемый отдельным доверенным
supervisor-ом через Docker API. Контейнер:

| Свойство | Значение |
|---|---|
| Сеть | `none` |
| Корень | только чтение (`read_only`) |
| Временная ФС | `tmpfs /tmp`, `noexec,nosuid`, 512 МБ |
| Память | 1 ГБ, swap 0 (`memory-swap` = `memory`) |
| CPU | 1 |
| PID | 64 |
| Пользователь | 65534:65534 |
| Capabilities | все сброшены |
| Привилегии | `no-new-privileges` |
| Системные вызовы | seccomp Docker по умолчанию, AppArmor `docker-default` |
| Монтирования | никаких: вход через stdin (tar), выход через `get_archive` |
| Окружение | пустое, без секретов |
| Образ | из allowlist supervisor-а, по digest, не от модели |
| Время | 60 с по умолчанию; до 600 с только по явному разрешению из общего бюджета заказа |

Убийство — через Docker API (`kill` контейнера), а не процесса-клиента: ядро
снимает весь cgroup. Supervisor ставит дедлайн сам.

### Проверено на этом хосте (Linux 6.17, cgroup v2, Docker runc 1.3.4, seccomp + AppArmor)

| Проверка | Результат |
|---|---|
| сеть `none` | `connect` → OSError |
| корень только чтение | запись в `/etc` → OSError |
| память 1 ГБ | OOM-kill, код 137 |
| PID 64 | `fork` остановлен на 63-м (BlockingIOError) |
| `tmpfs` 512 МБ | запись остановлена ровно на 512 МБ |
| uid и capabilities | `65534`, `CapEff` = 0 |
| убийство клиента `docker run` | **контейнер продолжил работу 60 с** |
| `docker kill` через API | 11 процессов сняты за 40 мс, контейнер удалён |

Отсюда правило: дедлайн и отмену исполняет supervisor вызовом API к
контейнеру; смерть клиента ничего не гарантирует. Страницы `tmpfs`
учитываются в лимите памяти cgroup.

## Контракт

**Вход** (`ScriptRunRequest`): `owner_key`, `work_order_id`, `step_id`,
`attempt_id`; `code_artifact_sha256` (код — артефакт, не строка в запросе);
`input_artifacts` — список `{artifact_id, sha256, name}` из брокера E28 (только
разрешённые); `runtime` — имя из allowlist (`python3.11`), сервер сам
сопоставляет его digest образа; `limits` — только уменьшение значений по
умолчанию, увеличение времени до 600 с — флаг, подписанный исполнителем по
бюджету заказа. Запрос подписан тем же HMAC, что жетон забора E24, и
привязан к попытке: supervisor проверяет, что попытка ещё владеет арендой.

**Выход** (`ScriptRunResult`): `status` ∈ {`succeeded`, `failed`, `timeout`,
`oom`, `refused`}, `exit_code`, `stdout`/`stderr` до 64 КБ каждый (с флагом
обрезки), `output_artifacts` — файлы из `/tmp/out`, до 20 файлов и 50 МБ,
каждый с sha256; `runtime_digest`, `limits_applied`, `started_at`,
`finished_at`. Запись `AgentScriptRun` и квитанция эффекта — в одном `commit`.

## Supervisor

Отдельный сервис `agent-script-supervisor`: единственный компонент с доступом
к Docker socket. Минимальный код, без выполнения команд по запросу: никаких
путей монтирования, команд или образов от модели. API аутентифицирован
сервисным ключом и подписью запроса, привязан к owner/work/action. Не
«shell как сервис». Работает от отдельного пользователя, без сети наружу.

## Модель угроз

| Угроза | Защита | Остаток |
|---|---|---|
| Выход из контейнера через ядро | seccomp, AppArmor, без capabilities, непривилегированный uid, user namespace | runc делит ядро с хостом → **gVisor** снимает основной класс |
| Исчерпание ресурсов | cgroup v2: память, CPU, PID, `tmpfs` | диск хоста не затрагивается (корень только чтение) |
| Утечка данных в сеть | сеть `none` | — |
| Доступ к секретам и БД | пустое окружение, нет монтирований, нет сети | — |
| Docker socket | только у supervisor-а | компрометация supervisor-а = root хоста; минимальный код, только API |
| Подмена образа | allowlist по digest | обновление образа — решение человека |
| Отравленный вход/выход | sha256, лимиты размера, брокер E28 | разбор выхода — работа получателя |
| Повтор запуска | квитанция E24 по ключу операции, забор аренды | — |
| Зависание | дедлайн и `kill` через API | — |
| Флуд логов | обрезка до 64 КБ | — |

## Отказ при недоступной изоляции

Supervisor недоступен, нет Docker, cgroup v2 не поддерживает нужные
контроллеры, образ не совпал с digest, runtime не из allowlist — запуск
отклоняется (`refused`) с причиной. Запасного исполнения в backend нет и не
будет.

## Решение владельца (открыто)

**gVisor (`runsc`)** как runtime запусков: системные вызовы кода
обрабатывает пользовательское ядро, и выход через уязвимость ядра хоста
практически исключается. Цена — установка пакета на хост и около 10–30 %
накладных расходов на системные вызовы. Сейчас не установлен. Supervisor
E27 принимает runtime из конфигурации (`runc` | `runsc`). Без gVisor
изоляция — уровень контейнера, с ним — уровень песочницы ядра.
