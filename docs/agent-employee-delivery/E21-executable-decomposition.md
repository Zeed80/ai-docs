# E21.3b — Исполнимая декомпозиция и исполнимые планы

Дата: 6 октября 2026. Исходный commit: `c7431353`. Исполнитель и приёмка:
Claude Code (root).

## Что было сломано

После E21.2b5 (вывод headless `agent_turn`) три пути создавали шаги, которые
могут только упасть, а не-чатовая работа (cron, API, декомпозиция) от этого
тихо умирала:

1. **Декомпозиция.** Шаг `decompose` создавал потомков без ledger и с одним
   `agent_turn`-шагом. Потомок не мог выполниться ни при каких условиях;
   `initialize_budget_ledger` не привязывает потомка к работающему родителю
   (у родителя уже есть история).
2. **Fallback планировщика.** Любой сбой detached-планировщика создавал план
   из одного `agent_turn`-шага → отказ → перепланирование → тот же отказ.
3. **Сам планировщик.** Промпт разрешал `agent_turn` «для синтеза» и при
   восстановлении после ошибки советовал «один agent_turn-шаг с итогом».

## Контракт

- `bind_child_to_parent_ledger`: новый потомок в той же транзакции
  привязывается к ledger родителя (тот же owner, неизменяемая привязка).
  Родитель без ledger → `BudgetBindingConflict`, ни один потомок не создаётся.
- Потомок остаётся `received` без плана; его планирует тот же durable
  capability-планировщик, вызов модели планировщика списывается с ledger
  родителя.
- Идемпотентность: потомки помечаются `decompose_spec_digest`; повтор шага
  (сбой после commit, до фиксации шага) возвращает тех же потомков.
- Сбой планировщика: событие `plan.planner_failed`, счётчик подряд идущих
  сбоев, план НЕ создаётся; следующий тик планирует снова. После
  `_MAX_CONSECUTIVE_PLANNER_FALLBACKS` (5) — `blocked`
  (`planner_schema_failure_streak`), как и раньше.
- `validate_capability_plan` отклоняет `agent_turn` с причиной, которую модель
  видит при следующей попытке; промпт разрешает только `capability` и
  `decompose`.
- Синхронный `plan_work_order(use_model=False)` (только `app_env == "test"`)
  не менялся.

## Тесты

планировщика с ledger родителя; родитель без ledger — отказ и откат;
план с `agent_turn` отклонён с причиной, без плана; 5-й сбой подряд блокирует.
Обновлены фикстуры: decompose (родитель с ledger, план потомка строит
«планировщик»), planner/exploratory (фейковая модель планирует capability-шаг),
политика fallback.

Регрессия: файлы work orders/planning/decompose — набор падений побайтово
совпадает с базовой линией (зависящие от порядка outbox/gap/telegram; отдельно
outbox 20 passed). Planner 23, verifier 17, ledger/lease/corpus 57,
`tests/ai` 3740 — passed.

## Остаток (следующий срез E21.3c)

Не-чатовой работе нужен durable-шаг **синтеза**: вызов модели без
инструментов под общим бюджетом (как planner/verifier contexts), на входе —
выводы завершённых шагов. Без него exploratory-задача не может выдать
обязательный итоговый отчёт о покрытии, а любая задача — связный итоговый
текст: результатом остаётся вывод последнего capability-шага.

# E21.3c — Durable-шаг синтеза и живой цикл не-чатовой работы

Шаг `synthesize` (`d58e6587`): планировщик ставит его последним, когда нужен
письменный ответ; один вызов локальной модели без инструментов через
direct-text границу попытки (общий ledger, usage receipt, не-локальный
провайдер — стоп до запроса). Exploratory-синтез сохраняет отчёт о покрытии.
