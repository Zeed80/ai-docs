# E39 — права по строкам для SQL агента (Postgres RLS)

Дата: 10 октября 2026. Решение владельца по ADR E38: вариант (б).

## Что было

SQL агента (`workspace.sql_table`) работал под ролями `agent_sql_reader` (семь
таблиц) и `agent_sql_reader_full` (все не секретные таблицы при полном доступе).
Права СУБД ограничивали таблицы, но не строки: инженер отдела A через агента
видел счета отдела B, а при полном доступе — чужую личную почту, чаты и память.

## Как устроено

- **Кто читает.** Конвейер (`table_sql_pipeline.execute_sql`) до перевода
  транзакции в read-only и до смены роли пишет строку в `agent_sql_actors`
  с ключом `pg_current_xact_id()`: sub пользователя, admin/manager, отдел и его
  поддерево. Пользователь берётся из `get_acting_user()`; в ходе от агента это
  человек из подписанного execution context, в durable-работе — владелец заказа.
  В конце запрос откатывается, и строка исчезает.
- **Почему не `SET LOCAL app.user_sub`.** `set_config` может вызвать любая роль,
  и SQL модели переписал бы пользователя. В `agent_sql_actors` у ролей агента нет
  ни записи, ни чтения: функции политик читают её как владелец
  (`SECURITY DEFINER`). Тест `test_the_reader_cannot_rebind_itself`.
- **Политики** (`app/ai/sql_row_security.py`, `RULES`) — `FOR SELECT TO`
  обеим ролям агента; приложение работает владельцем и их не видит.
  - Документы и всё производное (чанки, извлечения, evidence, чертежи, BOM,
    техпроцессы, счета и их строки, складские приходы): правило `visibility_filter`.
    admin/manager видят всё; остальные — своё, своё поддерево отделов и строки
    без владельца **и** без отдела.
  - Личное — только владелец, даже для admin, как в API: чаты, durable-работа,
    `owner:`-память, личные ящики (и только при `sweep_enabled`, как для агента
    в `email_access`), уведомления, коллекции, сохранённые запросы.
  - Ссылки на сущность (`entity_type`/`entity_id`: аномалии, согласования,
    комментарии, аудит) — как сама сущность.
  - Память: `project`/`global`, свой `owner:`, свой `department:`, свои сессии;
    неизвестная область скрыта.
- **Без пользователя** (headless без execution context, `agent-service`) видны
  только строки без владельца.
- **Без роли запроса нет.** Раньше обычный режим при отсутствии роли
  продолжал от владельца базы — теперь это обход RLS, поэтому отказ.
- **Установка** идемпотентна и идёт на старте backend (`install_row_security`):
  версия — хэш функций и правил в комментарии к `aiw_rls_sub()`; пропускается,
  если версия совпала и у каждой существующей таблицы из `RULES` есть политика.
  Там же создаются роли и права семи таблиц — база, поднятая из metadata без
  миграции `20260905_0001`, иначе осталась бы без SQL агента.
- **Покрытие.** `test_every_table_with_an_owner_has_a_rule_or_a_reason`: таблица
  с колонкой владельца или ссылкой на приватный объект обязана быть в `RULES`,
  в `COMPANY_WIDE` (с причиной) или среди секретных.

## Попутно исправлено

`visibility_filter` (API документов, счетов, дел, поиска памяти) считал
«legacy» строку без владельца **или** без отдела. Документ с владельцем, но без
отдела — загрузка, вложение личного ящика — был виден всем. Теперь legacy — это
ни владельца, ни отдела; так и было написано в docstring.
