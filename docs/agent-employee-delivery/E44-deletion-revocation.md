# E44 — удаление и отзыв во всех производных хранилищах

Дата: 10 октября 2026.

## Как устроено

- **Чтение закрывается сразу.** Права решает БД: API (`visibility_filter`,
  охрана `/{id}`), граф (`GraphAccess`), SQL агента (RLS), векторный поиск
  (перепроверка найденного по таблице документов). Смена владельца или отдела и
  удаление действуют с коммита; индекс может отставать только в полноте.
- **Кэши** с данными пользователя живут 15–20 с и привязаны к пользователю (E39).
- **Векторы**: удаление стирает все точки документа во всех `documents__*`;
  смена прав перепечатывает `acl` задачей после коммита; ночная синхронизация
  добирает пропущенное и удаляет сирот (E41).
- **Граф**: удаление документа удаляет его узлы, рёбра, упоминания и узлы-сироты.

## Найдено и исправлено

1. Узел, собранный регуляркой из текста документа (ИНН, адрес), без документной
   опоры считался «общими данными». Удалили единственный документ Bob — его ИНН
   стал бы виден всем. Теперь такой узел без опоры скрыт (`graph_access`,
   `aiw_rls_node`); общими остаются только узлы, созданные не построителем.
2. Файлы MinIO и векторы стирались внутри `hard_delete_document`, до коммита
   вызывающего: при сбое коммита документ оставался без файла. Теперь — по
   событию `after_commit` сессии; откат их отменяет.
3. Удаление документа не попадало в аудит. Теперь `doc.delete` (одиночное и
   массовое) с id и числами удалённых записей — без имени файла и текста.
4. Новая таблица версий блоков (E42) не имела политики RLS — поймал тест
   покрытия; правило «только владелец».

## Повтор и частичная очистка

Повторное удаление отвечает 404 и ничего не ломает. Если после коммита упало
стирание файла или векторов, это видно в журнале
(`document_delete_effect_failed`), а доступ не восстанавливается: строки
документа нет, перепроверка отбрасывает найденное, ночная синхронизация
удаляет сирот.

## Восстановление из старой резервной копии

Бэкап БД возвращает строки вместе с их владельцами и отделами того времени —
права после восстановления берутся из восстановленной БД. Векторный индекс при
этом сверяется ночной синхронизацией (`acl` из БД, сироты удаляются), так что
отозванное после бэкапа право не возвращается молча через индекс. Само решение
восстанавливать старый бэкап — операция администратора с журналом установщика.
