# `/work-orders` — руководство оператора (Б20)

Один экран на весь durable-runtime автономного исполнителя: список
поручений слева, план/evidence/approval/журнал/метрики выбранного
поручения справа. Обновляется опросом (список поручений — раз в 5 с,
детали выбранного — раз в 5 с, агрегированные метрики в шапке — раз в
30 с) — WebSocket пока не подключён (см. `AGENT_SYSTEM_REMEDIATION_PLAN.md`
Б13.5, отдельная нерешённая задача).

## Статусы поручения (`WorkOrder.status`)

| Статус | Что значит | Нормально ли ждать |
|---|---|---|
| `received` | Поручение создано, планирование ещё не началось | Секунды |
| `scoping` | Уточняются рамки задачи | Секунды |
| `planning` | Строится DAG-план из живого `capabilities.yml` | Секунды |
| `ready` | План готов, ждёт свободного шага для захвата диспетчером | Да, до следующего тика `work.dispatch_ready` (раз в 5 с) |
| `running` | Хотя бы один шаг сейчас исполняется | Да |
| `waiting_approval` | Шаг approval-gated, ждёт решения человека — см. карточку шага, кнопки «Одобрить»/«Отклонить» появляются прямо там | **Требует действия** — само не пройдёт |
| `waiting_external` | Ждёт что-то вне собственного графа шагов — сегодня единственный источник: родитель `decompose`-плана (Б11) ждёт завершения ВСЕХ дочерних поручений (видны как отдельные строки в списке слева, `parent_id` указывает на это) | Да, пока не завершится последний ребёнок |
| `verifying` | Независимый verifier проверяет criteria/evidence после успеха шага | Секунды |
| `replanning` | Шаг провалился, но лимит `budgets.max_replans` (по умолчанию 2) не исчерпан — план перестраивается | Да |
| `blocked` | **Не пройдёт само** — см. блок `blocker` (JSON) в карточке поручения: `token_budget_exceeded`, `verification_failed`, `independent_verification_required`, `lease_expired`, `all_children_failed`(через `verification_failed`, см. Б11) и т.д. | Нужно решение человека |
| `failed` | Провалился без права на реплан (лимит исчерпан) | Терминально |
| `completed` | Готово — `result_summary` содержит финальный текст | Терминально |
| `canceled` | Отменено вручную (кнопка «Отменить») | Терминально |

Если статус не входит в эту таблицу — в UI он получит серую заглушку
(`bg-slate-700`) вместо цветной подсветки; значит либо появился новый
статус в `WORK_TRANSITIONS` (`domain/work_orders.py`), либо это опечатка —
сверьтесь с исходником, не с этой таблицей задним числом.

## Статусы шага (`WorkStep.state`, видны на карточках в блоке «План»)

`pending` (ждёт зависимости) → `ready` (можно захватывать) → `running` →
`succeeded` / `retry_wait` (провал, будет ретрай) / `waiting_approval` /
`failed` (терминально для шага) / `skipped` / `canceled`.

Цветная полоса слева на карточке шага — уровень зависимости (топологическая
глубина от `depends_on`), не статус. Шаги одного цвета можно исполнять
параллельно; шаг следующего уровня ждёт предыдущий.

## Evidence — как читать

Под каждым шагом, если по нему были вызовы инструментов — свёрнутая строка
`▸ tool_call · <статус> · digest <первые 10 символов>`. Разверните клик —
покажет точные аргументы вызова и результат (или ошибку). Это тот самый
`WorkToolCall`, ради которого строился durable-слой: запись «что именно
вызвано» делается ДО вызова (write-ahead), поэтому digest виден даже если
сам вызов ещё выполняется или упал.

## Approval — когда шаг ждёт вас

Если шаг в статусе `waiting_approval`, прямо на его карточке появляется
жёлтый блок: точное имя capability.action и аргументы, которые будут
выполнены при одобрении — тот самый digest, что и в evidence, никаких
сюрпризов после нажатия «Одобрить». Одобрение/отклонение уходит через
`/api/approvals/{id}/decide` — тот же путь, что использует отдельная
страница `/approvals`, здесь просто виден в контексте конкретного шага.

## «Форсировать шаг вручную (debug)» — когда этим пользоваться

**Не основной способ работы.** Обычные шаги подхватывает автономный
диспетчер (`work.dispatch_ready`, Celery beat, каждые 5 секунд) сам, без
участия оператора. Эта кнопка (за подтверждением) — отладочный обход на
случай, если диспетчер явно завис или нужно продвинуть конкретное
поручение прямо сейчас для диагностики. Если приходится нажимать её
регулярно на живых поручениях — это сигнал, что автономный диспетчер не
работает, а не штатный режим использования; разбираться с диспетчером, не
привыкать к кнопке.

## Метрики в шапке

Блок над списком поручений (Б14) — агрегаты за окно (по умолчанию 24 ч):
счётчики по статусам + p50/p95 длительность успешных попыток по
`capability.kind`. Это не полноценный трейсинг — для «почему конкретный ход
пошёл этим путём» смотрите структурированные логи `agent_turn_complete`
(поле `plan_source`), не эту страницу (см. `AGENT_SYSTEM_REMEDIATION_PLAN.md`
A6 — эта телеметрия уже есть в логах секретаря, отдельная от durable-слоя).

## Журнал

Список внизу — сырые события (`work.status_changed`, `step.status_changed`,
`tool_call.prepared`, ...) в обратном хронологическом порядке. Полезен,
когда evidence/статуса недостаточно и нужно увидеть точную
последовательность переходов, включая кто (`actor`: `scheduler`, `policy`,
конкретный worker id, email пользователя) их инициировал.
