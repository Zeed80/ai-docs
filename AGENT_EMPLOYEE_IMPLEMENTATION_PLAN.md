# Универсальный цифровой сотрудник: реализация и остаток работ

Актуализировано: 11 сентября 2026 года. Этот документ уточняет агентскую часть
`CLAUDE.md`, `PLAN.md` и `DEVPLAN.md`. Roadmap в `docs/archive/` — история,
а не подтверждение готовности нового агента.

## Принятые решения

Цель — почти полная замена универсального сотрудника в цифровых процессах.
Первый целевой контур: браузер, файлы и внутренние API. Управление рабочим столом ОС
в первый выпуск не входит; существующие `desktop_*` относятся к браузерному сервису.

- Модель планирует и выбирает действия. Недоступность модели не запускает
  резервную последовательность из ключевых слов.
- Эвристики не определяют исполняемую процедуру или разрешение на действие.
  Детерминированные проверки типов, прав, лимитов и контрольных сумм сохраняются.
- Постоянно генерируемые скиллы, автоматическое продвижение, shadow-эксперименты
  на пользовательском трафике и replay рецептов по сходству запроса исключены.
- Память — факты, инструкции и свидетельства. Сходство помогает искать,
  но не является основанием исполнить сохранённую процедуру.
- Одноразовый Python-код допустим как артефакт задачи только в изоляции.
  Отключение старого runner не означает готовность нового.
- Автономность действует внутри явно выданных человеком полномочий; агент не
  выдаёт себе новые права и не подтверждает собственные предложения.
- Dual AI сохраняется: конфиденциальные данные локальны, облачный маршрут —
  только по решению оператора.

## Реализованный срез

### Личность и авторизация

- Подписанный короткоживущий `ExecutionContext`: владелец, адресат, версия, срок.
  Неподписанный `X-Acting-User` не меняет владельца запроса.
- Внутренний ключ больше не даёт admin. Подписанный актор разрешается в активного
  пользователя из БД с актуальной ролью, отделом и доступом к разделам.
- Human-only решения отвергают сервисный аккаунт и запросы `via_agent`.
- Viewer не может выполнять через шлюз операции с побочным эффектом;
  опциональная аутентификация использует тот же проверенный контекст.
- Подтверждение обязательно связано с аргументами digest.
- Ошибка downstream сохраняет HTTP-ошибку. Невозможность записать аудит блокирует
  действия с побочными эффектами до обращения к downstream.

### Каталог, память, события

- `ai/tool_catalog.py`: маршруты и явные эффекты. Read-only и параллельный запуск
  проверяются по каталогу, не по префиксам имён. Остальные старые policy-маркеры
  ещё требуют консолидации.
- Рабочие блоки в PostgreSQL с уникальным `(owner_key, block_key)`, без общего TTL.
  Старые общие Redis-блоки автоматически не присваиваются пользователям и не
  удалены миграцией; их перенос требует доказанного определения владельцев.
- Vault проверяет владельца и формат ссылки, не читает произвольные Redis-ключи.
- Глобальный ChatBus допускает только уведомления об изменениях без содержимого.
  Текст и результаты инструментов адресуются владельцу.
- Чужие owner/session scopes памяти отклоняются. SQL-поиск сообщений ограничен
  владельцем. Клиентский `trusted` не делает переписку общей памятью.
- Telegram требует непустого allowlist и привязки к активному пользователю.
  Работа с личными данными — только в личном чате; при перепривязке старая
  история сессии не передаётся новому владельцу.

### Планирование и runtime

- Активный вход оркестратора использует `TurnDecision`. Убраны replay рецептов,
  эвристическое исправление/исполнение workspace-действий и перестановка
  рекомендованных инструментов по исторической успешности.
- Генерируемый каталог не подключается. API запуска/продвижения и старый runner
  отвечают 410. Архивные исходники и история не удалены.
- Прямой shell в backend отключён: allowlist команды не изолирует её аргументы.
- Подтверждение отправки по ключевым словам отключено в активном цикле:
  требуется карточка подтверждения или постоянное ограниченное разрешение.
- Heartbeat и запись результата проверяют действующую аренду, worker и номер
  попытки. Verifier использует текущую ревизию плана и строгий boolean.
- Введён `ToolResult`, но перевод всех инструментов на контракт не завершён.

### Постоянные разрешения

- `GET/POST /api/agent/delegations`, `DELETE /api/agent/delegations/{id}`.
- Экран `/settings/delegations`: конкретные действия, точные JSON-ограничения
  аргументов, 1–200 попыток, срок 1–168 часов, расход и отзыв.
- Только свои разрешения и только реальный человек. Admin-операции, execute,
  неизвестные инструменты и пустые ограничения не делегируются.
- Шлюз повторно проверяет и атомарно расходует разрешение перед действием.
  Предварительная проверка чат-цикла не является доказательством разрешения.
- Неудачная попытка тоже расходует лимит. Отзыв не отменяет уже начатый вызов.
  Это не гарантия exactly-once и не замена доменных ACL.
- Telegram: `POST /api/agent/channels/telegram` с `owner_key`, `telegram_user_id`;
  отзыв — `DELETE /api/agent/channels/telegram/{id}`. Только администратор,
  после отдельной проверки принадлежности Telegram ID.

### Долговечный чат: переключённый UI и ограничения пилота

- `POST /api/agent/chat-runs` принимает `request_id` (UUID), `content`, необязательные
  `session_id` и `reasoning_mode`. Ответ 202 содержит ID чата, запуска и WorkOrder.
  Сообщение, задача, критерий приёмки и готовый шаг сохраняются одной транзакцией.
- Повтор того же запроса возвращает исходный запуск; другой ввод с тем же ключом
  даёт 409. PostgreSQL advisory lock защищает конкурентные повторы. В одном чате
  допускается один активный запуск; чужой чат не раскрывается (404).
- `GET /api/agent/chat-runs/{id}` возвращает состояние; `GET .../{id}/events?after=N`
  — сохранённые события с последовательностью и `next_cursor`. Клиент должен
  устранять повторы по sequence; событие `chat.done` не означает успешную приёмку.
- Beat обнаруживает готовую запись в БД; HTTP-запрос не запускает LLM и не держит
  исполнение. Worker использует ChatSession.id и сохраняет ответ в ChatMessage
  с `verified=false`; семантическая проверка остаётся отдельной стадией WorkOrder.
- Проверка аренды и сохранение события предшествуют вызову инструмента. Ошибка
  записи событий, истёкшая аренда и отмена останавливают запуск. Это не атомарное
  fencing внешнего сервиса: уже отправленное действие нельзя отозвать отменой.
- Пилот ограничен 200 вызовами инструментов и 2 часами исполнения. После потери
  worker — blocked, без автоматического повторения разговора: max_attempts=1,
  max_replans=0. Неизвестный результат внешнего действия требует сверки человеком.
- Постоянные разрешения применяются существующим шлюзом. Новое подтверждение
  сохраняется как событие `chat.confirmation_required`, затем блокирует запуск
  до действия. Карточка продолжения реализована 12 сентября (контракт ниже).
  Статус остаётся blocked, это не waiting_approval.
- Основной AssistantPanel переключён на HTTP-транспорт, включая отправку,
  восстановление запуска по ChatSession.id, cursor polling и отмену WorkOrder.
  Закрытие панели/вкладки не отменяет worker; `chat.done` не завершает UI до
  терминального состояния WorkOrder. Повтор транспортного POST использует тот
  же request_id. Уже загруженный из истории ответ не дублируется при replay.
- Смешивание старого WS и нового runtime в одном чате запрещено. Старая история
  в UI доступна только для чтения с пояснением: для работы нужен новый чат.
  Сам compatibility endpoint `/ws/chat` ещё существует для старых клиентов;
  основной UI и его health-probe больше к нему не подключаются.
- Вложения принимаются только для Document.owner_sub текущего пользователя;
  имена/размеры берутся из БД, а не клиентского JSON. Контекст рабочего экрана
  сохраняется во входе шага (лимит 64 KB), но не является источником полномочий.
- Запись checkpoint и продолжение остановленного подтверждения реализованы.
  Произвольный resume после сбоя по-прежнему запрещён. Старые
  `/work-orders/{id}/run` и `/instructions` не запускают/не перепланируют
  durable chat; отмена доступна через `/api/work-orders/{id}/cancel`.
- Схема `20260911_0001` добавляет `durable_chat_runs`, не удаляя существующие данные.
- Дополнительно усилена отмена: running-шаг и попытка переходят в canceled,
  аренда снимается; незавершённые вызовы получают outcome_unknown и требуют
  сверки. Worker повторно проверяет аренду между подготовкой и запуском вызова.
  Проверены отмена активного fake-agent через полный dispatch и отмена в окне
  между подготовкой вызова и его запуском, а также запрет переноса legacy-истории
  и остановка на слишком большом событии. Это ещё не аварийный E2E живого сервиса.
  Повторный целевой прогон после усиления отмены: 94 passed; Ruff прошёл.

### Реализован фундамент checkpoint — 11 сентября 2026

- `WorkStepAttempt.checkpoint` хранит снимок версии 1: текущие сообщения модели,
  системный контекст, отпечаток конфигурации, настройки роли, номер итерации,
  учтённые токены, оставшиеся вызовы с устойчивыми ID и текущий вызов.
- Точки записи: планирование группы инструментов, перед каждым вызовом, после
  добавления его результата в контекст, при новом подтверждении и после хода.
  Подтверждение сохраняет точные аргументы ожидающего действия; прежние результаты
  не исчезают при переводе попытки в failed/blocked.
- Снимок — независимый JSON с SHA-256 и лимитом 4 MB. Запись проверяет владельца,
  WorkOrder, шаг, попытку, аренду и активную ревизию плана. Ошибка сохранения
  пересекает обычные recovery-обработчики модели и не допускает следующий вызов.
- Пока нет атомарного журнала параллельных результатов, durable-исполнитель
  выполняет инструменты последовательно. Старые неприкреплённые к checkpoint
  AgentSession сохраняют прежний режим параллельности.
- `GET /api/agent/chat-runs/{id}/checkpoint` показывает владельцу только состояние,
  фазу, количество ожидающих инструментов и hash; сообщения/системный контекст
  через этот API не выдаются. Чужая задача → 404, неверная привязка/целостность → 409.
- На этапе фундамента `can_resume=false` оставался обязательным. Снимок не является разрешением
  повторить действие и не доказывает, что внешний эффект не произошёл.
  Переход подтверждения добавлен следующим срезом; общий журнал результатов
  логических действий и сверка неизвестных эффектов ещё необходимы.
- Проверка: `python3 -m pytest backend/tests/test_chat_checkpoints.py backend/tests/test_durable_chat.py -q`.
  Новая миграция не нужна: используется существующая колонка checkpoint.
- Целевой backend-прогон с role-dispatch: 113 passed. Существующие предупреждения:
  неизвестная настройка pytest `asyncio_loop_scope` и async mock синхронного
  memory-hook в role-dispatch тесте. Полного прогона репозитория и живой LLM не было.
- Выполнен `make prod-build`: backend/frontend/workers healthy, `/health` → ok,
  новый checkpoint API без авторизации → 401; хеши развёрнутых модулей совпали.

### Продолжение после подтверждения владельца — 12 сентября 2026

- `POST /api/agent/chat-runs/{id}/resume` принимает `attempt_id`, `sha256`,
  строго булевый `approved`. Только владелец-человек; агентский контекст запрещён.
  Проверяются привязка снимка, ревизия, failed-попытка, точный ожидающий вызов и
  аргументы. Только фаза confirmation_required, не tool_started после сбоя.
- Решение сохраняется в `chat.continuation_decided`. Блокировки разговора и работы
  сериализуют двойное нажатие и новый ход. Повтор того же решения идемпотентен;
  изменить решение нельзя. Более новый ход делает старый снимок непродолжаемым.
- Согласие создаёт новую ревизию плана и один шаг, привязанный к решению.
  Worker восстанавливает контекст модели, системный контекст, роль, счётчики и
  оставшийся список вызовов; исходный запрос и завершённые инструменты не повторяет.
  Планировщик orchestrator повторно не запускается: это продолжение executor.
  Итог остаётся предметом независимой приёмки WorkOrder, а не автоматическим успехом.
- Согласие потребляется только конкретным call_id с теми же аргументами;
  следующий вызов даже с теми же аргументами требует нового решения. Срок —
  30 минут после решения; изменённая конфигурация запрещает продолжение.
  Общий двухчасовой лимит работы не сбрасывается и проверяется на границах worker.
- Отказ оставляет работу blocked без эффекта и закрывает решение этого снимка.
  Потеря worker во время внешнего действия остаётся blocked без автоматического
  повтора: общего exactly-once для внешних систем этот механизм не обещает.
- GET checkpoint показывает владельцу точные аргументы только доступного
  подтверждения, без истории модели. `can_resume` вычисляет сервер; флаг в
  сохранённом снимке остаётся false и не является разрешением.
- UI восстанавливает карточку после reload. Автоподтверждение и редактирование
  аргументов для неё отсутствуют. Продолжение читает события с прежнего cursor;
  транспортный повтор отправляет то же решение, не создаёт новое сообщение.
- Проверено: 126 целевых backend-тестов, 45 frontend unit-тестов, typecheck,
  Ruff; 2 Chromium-сценария с подставным API. Существующие предупреждения:
  pytest asyncio_loop_scope, async mock memory-hook в role-dispatch, два ESLint
  предупреждения в AssistantPanel. Живые LLM и внешняя отправка не проверялись.
- Миграция не нужна: используются существующие WorkEvent/WorkPlan/WorkStep.
- Production: `make prod-build` завершён, backend/frontend/workers healthy,
  `/health` → ok. POST resume без CSRF → 403; с CSRF без авторизации → 401,
  GET checkpoint без авторизации → 401. Хеши backend/worker совпали с рабочими
  файлами; frontend bundle содержит новую карточку. Реальные внешние действия
  при проверке production не запускались.

### Журнал логических действий и наблюдения владельца — 12 сентября 2026

- Миграция `20260912_0001` добавляет `chat_logical_actions`. Серверный UUID
  создаётся до вызова и сохраняется при продолжении подтверждения. Повторяемый
  моделью call_id не является идентификатором действия: новый batch получает
  новые UUID. Карта UUID хранится отдельно от сообщений модели.
- Запрос, его хеш, текущая попытка и состояние сохраняются в той же транзакции,
  что и checkpoint. Сохранённый результат и его хеш также атомарны с checkpoint;
  события planned/started/waiting_confirmation/result_recorded содержат UUID.
  Сбой записи до вызова не допускает эффект; сбой после вызова останавливает
  оставшиеся инструменты и оставляет результат неизвестным.
- `result_recorded` означает наличие ответа, не успешный или проверенный внешний
  эффект. Явный структурированный `status=outcome_unknown` сохраняется как unknown.
  У начатого вызова без результата потеря lease, завершение попытки или остановка
  работы дают `outcome_unknown` при чтении, без ожидания прохода scheduler.
- Только владелец читает `GET /api/agent/chat-runs/{id}/actions` (метаданные,
  offset/limit) и `GET /{id}/actions/{action_id}` (точный запрос и результат).
  Список не загружает целиком большие аргументы/результаты. Детальный API
  проверяет хеши; приватный системный контекст и история модели не выдаются.
- `POST /{id}/actions/{action_id}/observations`: `request_id`, `request_digest`,
  `outcome=observed|not_observed|inconclusive`, непустые `note` и `evidence_reference`.
  Только владелец-человек и только остановленная работа с неизвестным исходом.
  Конкурирующие одинаковые запросы дают одну запись; изменение того же request_id
  запрещено. Можно добавить новое наблюдение, не стирая прежние события.
- Наблюдение имеет `verified=false` и `can_replay=false`. Оно не меняет состояние
  работы, не разрешает повтор и не делает слова человека независимым доказательством.
  Произвольные ссылки не загружаются автоматически. Экран сверки пока не добавлен.
- Покрытие — только действия, реально записанные новым worker. Старые результаты
  из истории не домысливаются; API явно возвращает `coverage=journaled_actions_only`.
  Продолжение старого подтверждения начинает журнал с ожидающего вызова.
- **Остаток:** передача логического ключа доменному получателю, атомарные receipts
  на его стороне, безопасные read-only проверки эффекта, UI сверки и правила
  продолжения по проверенным свидетельствам. Журнал не даёт общего exactly-once.
- Проверено: 139 целевых backend-тестов, в том числе настоящие worker/checkpoint
  границы с отказом записи, rollback результата вместе со снимком, потеря lease,
  защита идентичности и API, конкурентные наблюдения, upgrade/downgrade миграции
  в отдельной PostgreSQL-схеме. Ruff прошёл; прежние шесть pytest-предупреждений
  остаются (asyncio_loop_scope и async mock memory-hook). Внешние эффекты и живая
  LLM при этих тестах не запускались.
- Production: `make prod-build` завершён; backend/frontend/workers healthy,
  `/health` → ok, Alembic `20260912_0001 (head)`. API журнала и наблюдений без
  авторизации → 401 (POST с CSRF). Хеши backend/worker совпали с рабочими файлами.
  Frontend typecheck прошёл; UI-код в этом срезе не менялся.

## Оставшиеся этапы — не считать реализованными

### 1. Единый долговечный runtime — следующий основной этап

1. Расширить переключённый HTTP-чат на остальные каналы и безопасную миграцию
   архивных разговоров; ChatSession.id уже является идентификатором разговора.
2. Удалить старый WS lifecycle после миграции внешних клиентов. Основной UI уже
   принимает команды через HTTP и читает сохранённые события без владения worker.
3. Устойчивый sequence событий, cursor возобновления, транзакционный outbox;
   повторная доставка не дублирует сообщения.
4. Расширить реализованное одноразовое подтверждение на остальные каналы;
   добавить UI сверки неизвестных эффектов и проверки получателей поверх
   реализованного журнала логических действий.
5. Pause/resume/cancel/replan через единую state machine. Fencing распространяется
   на каждый вложенный tool call и доменную запись, не только результат шага.
6. Бюджеты по умолчанию: 2 часа активного времени, 200 tool calls, 50 LLM calls,
   3 replans. Одинаковый учёт чата, расписания, Telegram и дочерних работ.

Приёмка: реальные рестарты backend/worker, отключения браузера, повторная доставка,
устаревшие worker; ни потери результата, ни повторного внешнего действия.

### 2. Результаты, идемпотентность и доказательства

1. Все инструменты возвращают ToolResult; partial/waiting_approval/outcome_unknown
   не считаются успехом.
2. Устойчивый ключ логического действия сохраняется до вызова и не меняется при
   техническом повторе. Получатель атомарно сохраняет результат этого ключа.
3. Timeout после отправки — outcome_unknown и сверка с получателем, не слепой retry.
4. Критерии приёмки до исполнения; непустой ответ не доказывает выполнение.
5. Проверка связана с ревизией артефакта и независимыми свидетельствами.

### 3. Одноразовые скрипты

Новый супервизор с отдельным процессом и обеспечиваемой ядром изоляцией на каждый
ScriptRun. Без секретов, общей файловой системы приложения, Docker socket и сети.
Только явно переданные входные файлы; результаты забирает брокер.

Начальные лимиты: 1 CPU, 1 GB RAM, 64 PID, 512 MB временного диска, 60 секунд;
продление до 600 секунд — явное решение в рамках бюджета. Ограниченные stdout/stderr,
уничтожение всей группы процессов, проверка symlink/path traversal и хеши артефактов.
Код не импортируется в backend и не становится постоянным tool.

Приёмка: бесконечный импорт, fork bomb, сеть/DNS, чтение секретов, выход за каталог,
заполнение диска, зависшие дочерние процессы. Python timeout/AST — не изоляция.

### 4. Браузерный сотрудник

DOM/accessibility, вкладки, формы, файлы, сессии с владельцем, handoff для login/MFA/
CAPTCHA. SSRF/private-network проверки редиректов и всех запросов. Секреты вводит
брокер, не LLM. Наличие browser_fetch и `desktop_*` не означает завершение этапа.

### 5. Полная изоляция знаний и артефактов

Единый ACL MemoryFact/графа/чанков/документов/писем/embeddings/артефактов. Версии
вместо перезаписи блоков, явное совместное использование и управляемое удаление.
Полная проверка graph/vector retrieval ещё не выполнена. Перенос общей старой
памяти только с доказанным владельцем.

### 6. UX и эксплуатация

Единая страница работ с управлением исполнением, бюджетами, подтверждениями,
источниками, версиями и расходами всех провайдеров. Конструктор разрешений с
понятными полями вместо технического JSON. Удаление настроек retired skills и
неиспользуемых эвристических помощников после миграции клиентов.

### 7. Приёмочный корпус и выпуск

120 синтетических задач по браузеру, файлам, данным, коммуникациям и координации,
по три запуска; отдельно prompt injection, чужие scopes, просроченные разрешения,
повторы, рестарты и недоступные провайдеры. Цель: ≥90% успешных задач в целом,
≥85% в каждой группе, ноль неразрешённых внешних действий и межпользовательских
утечек. Эти значения — целевые, не измеренный результат текущего среза.

## Проверка и выпуск

Из корня репозитория:

```bash
python3 -m pytest backend/tests/test_agent_execution_boundary.py backend/tests/test_agent_delegations.py -q
python3 -m pytest backend/tests/test_durable_chat.py backend/tests/test_work_order_checkpoint.py -q
python3 -m pytest backend/tests/test_auth_acting.py backend/tests/test_capability_router.py backend/tests/test_work_order_verifier.py backend/tests/test_work_order_lease.py -q
make prod-build
curl -k https://localhost/health
```

Проверка frontend: `npm run typecheck` в `frontend/`.
Миграция `20260910_0001` добавляет четыре таблицы без удаления старых данных.
Upgrade/downgrade проверяется в отдельной схеме тестового PostgreSQL. API-тесты
направляют внутренние сессии в тестовую транзакцию, не в DATABASE_URL приложения.
Не запускать pytest на production DB.

Полная приёмка универсального сотрудника не выполнена. Фактические результаты
тестов и deployment сообщаются отдельно; unit-тесты не заменяют end-to-end корпус.
