# Находки живого теста агента (2026-08-19)

Источник: живой прогон 11 реалистичных сценариев + 1 multi-turn сценарий
через `/ws/chat` на боевом стеке (`infra-backend-1`, реальный Postgres).
Скрипт: `agent_live_scenarios.py` (сохранён в scratchpad сессии). Полные
результаты: `/tmp/live_scenario_results.json` в контейнере `infra-backend-1`
(там же, где был проведён прогон — путь внутри контейнера, не сохранён в репо).

Статусы: ✅ исправлено · 🟡 смягчено (частичный фикс/guidance) · ⏸ отложено
(осознанное решение, не баг) · 📝 задокументировано как известное ограничение.

## №1 — Напоминание получает дату из «памяти» модели, а не из реального времени ✅

**Сценарий:** `reminder` — «Напомни мне завтра утром проверить остатки на
складе», запущено 2026-08-15.
**Симптом:** агент посчитал «завтра» как 16 августа **2025** — на год в
прошлом; такое напоминание `remind_at` в прошлом, что либо создаёт
немедленно «просроченный» reminder, либо (в зависимости от даунстрим-логики)
никогда не сработает как обещано.
**Причина:** нигде в построении system prompt (`_load_system_prompt`,
`_effective_system` в `backend/app/ai/agent_loop.py`) не было ни одной
инъекции текущей даты/времени. Относительные даты модель считала от
собственного «внутреннего» ощущения времени (обучающих данных), а не от
реальных часов деплоя.
**Фикс:** `backend/app/ai/agent_loop.py` — новая функция `_today_context()`
(ISO-дата + русская человекочитаемая форма + день недели + время),
вызывается в `_effective_system()` **на каждый вызов** (не один раз при
старте сессии — иначе сессия, пережившая полночь, продолжала бы видеть
вчерашнюю дату).
**Severity:** высокая — агент подтверждал выполнение обещания («Утром
напомню»), которое физически не могло сработать корректно.

## №2 — `calendar_create_reminder` требовал entity_type/entity_id даже для отдельного напоминания ✅

**Сценарий:** тот же `reminder`.
**Симптом:** LLM была вынуждена подставить `entity_type`/`entity_id` под
запрос, который ни к какой сущности не привязан («проверить остатки на
складе» — не счёт, не поставщик, не документ).
**Причина:** `ReminderCreate` (`backend/app/domain/calendar.py`) объявляла
оба поля обязательными, в отличие от аналогичной `CalendarEventCreate`, где
`entity_type`/`entity_id` уже опциональны.
**Фикс:** оба поля сделаны `| None = None` в Pydantic-схеме, в
SQLAlchemy-модели `Reminder` (`backend/app/db/models.py`, nullable=True) и
в миграции `20260819_0008_reminder_entity_nullable.py`.

## №3 — `entity_id` не проверялся на существование сущности ✅

**Сценарий:** тот же `reminder`.
**Симптом:** в одном из прогонов модель подставила заведомо фиктивный
UUID-плейсхолдер (`00000000-…-000000000001`) — запрос прошёл валидацию
Pydantic (это просто валидный UUID) и был молча записан в БД.
**Фикс:** `create_reminder` (`backend/app/api/calendar.py`) теперь при
переданных `entity_type` + `entity_id` из известного набора
(`invoice`/`supplier`/`document`) проверяет существование записи через
`SELECT` и возвращает `404`, если сущности нет. Неизвестные `entity_type`
пропускаются без проверки (не хотим держать в calendar-модуле
исчерпывающий реестр всех типов сущностей).

## №4 — Схема `body` для `calendar_create_reminder` была недокументирована ✅

**Сценарий:** тот же `reminder` — 5 вызовов `analytics` вместо одного.
**Симптом:** LLM перебрала поля `title`/`description`/`date`/`time`, прежде
чем случайно попасть в правильную схему `entity_type`/`entity_id`/
`remind_at`/`message`.
**Причина:** в `aiagent/skills/capabilities.yml` поле `body` для capability
`analytics` описывалось общей фразой «Данные для create/update/import» без
разбивки по конкретным `action`.
**Фикс:** описание `body` расширено точной схемой для
`calendar_create_reminder` (обязательные/опциональные поля, явное указание
не выдумывать UUID). Остальные `action` пока не документированы так же
подробно — сделать по мере обнаружения похожих проблем на живых тестах,
чтобы не плодить неточную документацию по наитию.

## №5 — Запрос к несуществующему поставщику молча даёт «0 из 0», а не явный ответ ✅

**Сценарии:** `invoice_lookup`, `email_draft` (оба про поставщика «ЦНК»).
**Проверено на реальной БД:** поставщика «ЦНК» в базе действительно нет
(проверено прямым SQL к `infra-postgres-1`/`aiworkspace`) — тестовый промпт
сослался на вымышленное имя. Но независимо от того, существует сущность или
нет, наблюдаемое поведение агента — паттерн, а не совпадение: он публикует
на Рабочий стол пустые 0-строчные таблицы и рапортует «Оставил на Рабочем
столе товары поставщика цнк: 0 из 0» вместо прямого «Поставщик «ЦНК» не
найден».

**Первая попытка (system-prompt-уровневая):** добавлен явный принцип в
`_OPERATIONAL_POLICY` (`backend/app/ai/agent_loop.py`) — пустой результат
это ответ, не повод имитировать выполнение. Живой тест показал, что этого
недостаточно: модель не всегда следует текстовой инструкции глубоко внутри
system prompt, ЦНК-таблицы продолжали публиковаться.

**Код-level фикс:** пустой результат от фильтра по имени поставщика
неоднозначен — либо поставщик существует, но у него пока нет счетов (реальное,
полезное пустое состояние), либо имя вообще ни с кем не совпадает (случай
ЦНК). Различение вынесено из «усмотрения» LLM в код обоих мест, которые могут
публиковать такую таблицу:
- `backend/app/api/workspace.py` (`publish_invoice_items_table`) — при
  `supplier_query` и 0 строк отдельная лёгкая проверка существования
  (`SELECT count(*) FROM parties WHERE name ILIKE …`, без join на invoices)
  отличает «поставщик есть, счетов нет» от «такого поставщика нет». Во
  втором случае — `status="not_found"`, `upsert_workspace_block` не
  вызывается вообще, пустой блок не создаётся.
- `backend/app/domain/table_spec.py` (`execute_spec`) — новое поле
  `TableResult.unresolved_entity`, тем же способом для любого спека с
  фильтром `supplier_name` и 0 строк. `backend/app/api/spec_tables.py`
  (`_render_and_publish`) возвращает `status="not_found"` и пропускает
  публикацию, если поле установлено.

**Побочный эффект, найденный и исправленный при живой проверке:** возврат
`not_found` без публикации блока сначала ломал audit-гейт
`_should_report_capability_gap` (`plan.workspace.required and not
audit.workspace_verified`) — раз блок не опубликован, аудит решал, что это
пробел в возможностях, и запускал полноценное предложение построить новый
capability `supplier_invoice_summary_publish` для запроса, на который агент
уже корректно и полностью ответил текстом. Добавлен
`AgentOrchestrator._has_not_found_tool_result()`: если хоть один инструмент
в ходе вернул `status="not_found"`, требование workspace считается
выполненным даже без публикации — узкое исключение (не любой
неопубликованный workspace-обязательный ход, только явный `not_found`), так
что настоящий пропуск (воркер вообще не вызвал workspace tool) по-прежнему
флагуется.

**Тесты:** 7 новых — 2 в `test_agent_workspace_realistic.py` (не найден →
блок не создаётся; реальный поставщик с 0 счетами → блок всё равно
создаётся), 3 в `test_spec_tables.py` (`execute_spec` различает случаи +
1 API-тест на `not_found`), 2 в `test_audit_quality.py` (audit-гейт
удовлетворяется `not_found`; настоящий пропуск по-прежнему флагуется). Все
77 тестов затронутых файлов зелёные на реальном Postgres.

**Живая проверка (секундомер, после rebuild+redeploy, x2 итерации):**
финальный текст хода для ЦНК — «...Поставщик «цнк» не найден в базе.» (без
финального 0-строчного блока для ЦНК). До второго фикса `approval_requests`
содержал предложение `supplier_invoice_summary_publish` — после фикса
`approval_requests: []`. Итоговый секундомер финального прогона: **257s**
(один длинный ход — ЦНК по-прежнему занимает 130-310s из-за большого числа
пробных вызовов, это отдельный аспект, см. ниже).

**Осталось открытым (не входило в объём этого фикса):** ход для ЦНК всё
ещё делает много «боковых» вызовов, прежде чем прийти к правильному
выводу — в одном из прогонов агент по пути опубликовал полный
неотфильтрованный список из 152 счетов и таблицу по совсем другому
поставщику («ООО ИПЦ», которого он нашёл по совпадению «CNIC» в описании
товарных позиций — не ошибка сопоставления, реальный текстовый матч, но
всё равно уводит от вопроса). Ни один из этих промежуточных блоков не
пустой и не подписан как относящийся к ЦНК, так что заявленная находка
(«не публикует пустую таблицу для ЦНК») закрыта, но общая «неэффективность
исследования» неизвестной сущности — это по-прежнему находки №7/№8,
отдельная, более масштабная задача.

## №6 — «Утверди счёт в статусе на проверке» при 0 таких счетов даёт сырой SQL-дамп вместо ответа 🟡

**Сценарий:** `approval_gate`.
**Проверено на реальной БД:** в базе действительно 152 счёта и **все** в
статусе `approved` — счетов `needs_review` нет вообще. Это не баг теста, а
факт данных: правильный ответ агента — «Счетов в статусе на проверке сейчас
нет», а не публикация таблицы «Количество счетов по статусам» с SQL-запросом
в качестве текста ответа.
**Фикс:** тот же новый принцип в `_OPERATIONAL_POLICY` (см. №5) — единая
формулировка покрывает оба случая («сущность не найдена» и «фильтр дал 0
строк»).
**Статус:** 🟡 — как и №5, нужна живая перепроверка.

## №7 — Составные вопросы получают неполный ответ 📝

**Сценарий:** `suppliers` — «Сколько всего поставщиков в базе? Кто из них
самый крупный по обороту?». Агент ответил только на первую часть («Всего
поставщиков: 39»), вторая часть проигнорирована.
**Оценка:** системная проблема планирования составных запросов, не
локальный баг одного capability. Быстрого точечного фикса нет — исправление
потребовало бы либо явного разбиения составных вопросов на подзадачи в
роутере (`route_table.py`), либо усиления prompt guidance с риском
регрессии на простых вопросах.
**Решение:** задокументировано как известное ограничение, не фиксится в
рамках этого прохода. Кандидат для отдельной инициативы, если паттерн
подтвердится на большем числе живых прогонов.

## №8 — Неизвестная сущность в запросе тратит несколько попыток ⏸

**Сценарии:** `invoice_lookup`, `email_draft` — по 3-5 вызовов инструментов
вместо 1-2.
**Оценка:** отчасти пересекается с №4 (недокументированная схема тратила
попытки) и с №5/№6 (агент не останавливается на первом же пустом
результате, а пробует альтернативные запросы). Оба этих фикса должны
частично снизить число лишних попыток естественным образом.
**Решение:** отдельного точечного фикса не делаем — перепроверить на живом
стеке после фиксов №4/№5/№6; если проблема сохранится, заводить отдельную
находку с точным причинным разбором.

## №9 — Race в `current_turn`: клиент видит «done», но следующее сообщение отклоняется ✅

**Сценарий:** `multi_turn` — второе сообщение сразу после первого получило
`error: "Предыдущая задача ещё выполняется."`, хотя клиент уже получил кадр
`done` для первого сообщения.
**Причина:** `backend/app/api/agent.py` (`/ws/chat`) проверял готовность к
следующему сообщению через `current_turn.done()` — а `asyncio.Task`
считается `done()` только когда корутина `on_user_message()` **полностью
вернула управление**, что включает работу ПОСЛЕ отправки клиенту кадра
`done`/`error` (персист сообщения в БД, аудит и т.п.). Существовал
параллельный флаг `turn_in_progress`, специально заведённый под этот кейс
(флипается в `False` ровно в момент отправки `done`/`error` — до персиста),
но реально нигде не использовался для гейта.
**Фикс:** гейт теперь требует **оба** условия — `turn_in_progress` И
`current_turn` не done. Так безопаснее чистого переключения на один
`turn_in_progress`: если `on_user_message()` упадёт с necaught-исключением
до отправки финального кадра (turn_in_progress тогда никогда не станет
`False`), сессия всё равно разблокируется, как только сама Task завершится
(с исключением) — как и было в исходном коде.

## №10 — `invoice_lookup` (150s таймаут) — РАЗОБРАНО: не баг, ложная тревога от слишком тугого клиентского таймаута теста ⏸→❌ опровергнуто

**Первоначальное наблюдение:** повторный прогон `invoice_lookup` после
фиксов не уложился в 150s клиентского таймаута тестового скрипта. По логам
контейнера турн успел пройти reranking-фолбэк (2× `404` на `/api/embed` +
`ai_route_reranker_empty_scores`) и `POST /api/memory/query 200` за 2982ms —
всё это заняло первые ~0.03s хода — а дальше в логах не было НИ ОДНОЙ
строки почти 2.5 минуты, что изначально выглядело как зависание где-то в
reranking/memory-query цепочке без таймаута.

**Разбор:** `OllamaProvider.rerank` (`backend/app/ai/providers/ollama.py`)
оборачивает каждый HTTP-вызов в `httpx.AsyncClient(timeout=…)` — таймауты
везде проставлены, и по логам этот фрагмент отработал штатно и быстро (все
три кандидата перебраны за миллисекунды). Значит зависал не reranking, а
что-то ПОСЛЕ него — и единственное, что идёт следом в ходе агента — основной
reasoning-вызов LLM (`config.llm_timeout_seconds`, дефолт **600s**, см.
`backend/app/ai/agent_config.py:77`, используется в `agent_loop.py:864/1119/1339`).
При потоковой (`stream`) генерации у Ollama httpx-таймаут применяется
per-chunk (к каждому отдельному read), а не как единый дедлайн на весь
ответ — пока модель продолжает присылать токены (пусть редко), ни один
read-timeout не срабатывает, и вызов может идти минутами без единой строки
лога, оставаясь при этом полностью живым.

**Проверка гипотезы:** повторный прогон ТОЛЬКО `invoice_lookup` с клиентским
таймаутом теста, увеличенным со 150s до 400s — **завершился успешно за
131.5s**, с ответом «Оставил на Рабочем столе товары поставщика цнк: 0 из
0» и 9 вызовами инструментов (`invoices`, `suppliers`×4, **`search`** —
агент даже попробовал веб-поиск по несуществующему поставщику, прежде чем
сдаться). Значит предыдущий таймаут в 150s был у теста, а не у сервера —
турн с таким количеством раундов планирования для несуществующего
поставщика естественным образом занимает 130-200+ секунд на используемой
здесь локальной модели (без выделенного быстрого GPU-инференса).

**Вывод:** №10 закрыт как ложная тревога инструмента верификации, а не как
находка о коде агента. Реальная (уже задокументированная) проблема — то,
что видно в 9 вызовах инструментов: агент не останавливается быстро на
неизвестной сущности и доходит даже до веб-поиска вместо прямого «Поставщик
не найден» после первых 1-2 безуспешных попыток — это то же самое, что
уже описано в №5/№8, отдельного фикса не требует, но подтверждает их
серьёзность (лишние 6+ вызовов инструментов и минуты ожидания на пустой
результат).
**Статус:** ❌ не баг / ⏸ дальнейшая работа переносится в рамки уже
запланированного фикса №5/№8 (принцип «пустой результат — это ответ»
из `_OPERATIONAL_POLICY` должен в идеале прерывать цепочку раньше — после
1-2 неудачных попыток, а не после 6).

## №11 — эвристический planner всегда подмешивал `memory.search` даже когда SQL уже нашёл точный фильтр по имени поставщика ✅

**Обнаружено:** при разборе находки №10 — почему `invoice_lookup` для «ЦНК»
делает так много вызовов и явно уходит в GPU-путь (`memory` → embedding +
reranking fallback-цепочка).

**Причина:** `AgentOrchestrator._plan_turn` (`backend/app/ai/orchestrator.py`,
эвристический fallback-планировщик, срабатывает когда `route_table.py` не
даёт точного keyword-совпадения — это ровно `"plan_source": "heuristic"` в
логах). Внутри уже есть `_extract_supplier_name(text)` — регекс, который
детерминированно достаёт «ЦНК» из текста и кладёт точный SQL-фильтр
(`workspace_filters={"supplier_query": "ЦНК"}`) для `workspace.spec_table`.
Но подсказка `skills` для LLM всегда была `["workspace.spec_table",
"memory.search"]` — то есть даже когда SQL-фильтр уже гарантированно
закрывает вопрос, hint всё равно предлагал модели ещё и семантический
memory-путь. LLM, получив такую подсказку, разумно дёргала оба — отсюда
лишний `memory` tool call и вся его GPU-цепочка (reranking, ollama /api/embed
и т.д.), которая и создавала впечатление «зависания» в №10.

**Фикс:** `backend/app/ai/orchestrator.py` — когда `supplier_name` извлечён
и `workspace_required` истинно, hint теперь **только**
`["workspace.spec_table"]`, без `memory.search`. Ветка без извлечённого
имени (обычные bulk/listing-запросы без конкретной сущности) не менялась —
там `memory.search` по-прежнему полезен, SQL не на что фильтровать. Заодно
поправлен устаревший комментарий в `model_registry.yaml`: `local_embedding_ollama`
(nomic-embed-text, 768-dim) был помечен как «текущая прод-модель для
существующей 768-мерной Qdrant-коллекции» — неверно. Живая проверка через
Qdrant API: все 6 коллекций (`documents/*`, `recipe_triggers/*`,
`correction_triggers/*` и легаси-имена) реально **4096-мерные**, под
`qwen3_embedding_8b_ollama` (совпадает с `ai_config.embedding_model`); nomic
зарегистрирован только как второй кандидат в `embedding.fallback_chain`, не
как активная модель. Комментарий переписан по факту.

**Тесты:** `backend/tests/test_router_dispatch.py` — 3 новых теста на все
три формы hint'а (`_plan_turn`): с извлечённым именем поставщика (только

## №13 — «Найди каталог поставщика и прикрепи к нему» — агент физически не мог это сделать ✅

**Сценарий (живой чат, 2026-08-21, сессия «Поиск каталогов для Мир
Станочника», `chat_sessions.id=4e6866de-…`):** «Найди в web каталоги на
поставщика ООО Мир Станочника и загрузи в его каталог», затем уточнение
«Я же тебя просил каталог найти. Посмотри на их сайте и прикрепи к данному
поставщику».

**Что агент сделал:** первый ход — опубликовал таблицу товаров этого
поставщика **из счетов** (`workspace.spec_table` + `workspace.invoice_items_table`,
5 строк). Второй ход — реально нашёл сайт и PDF-каталог СКИФ-М
(`search.browse`), но «прикрепил» их как две заметки в реестре источников
(`memory.source_propose`) и опубликовал таблицу «найденные каталоги» (4 строки).
В каталог поставщика не попало ничего.

**Четыре независимые причины (все исправлены):**

1. **Инструмента не было видно.** Capability `tool_catalog` (Ф3) не входила
   ни в один role-allowlist `gateway.yml`, а `_tools_for_turn` фильтрует
   инструменты по роли. Роль хода — `data_analyst` → `tool_catalog`
   отсутствовала в списке инструментов вообще, и модель выбрала ближайшее
   доступное (`memory.source_propose`).
   *Фикс:* `tool_catalog` добавлена в 6 ролей; плюс структурный —
   `AgentSession.set_recommended_capabilities()`: capability, которую
   планировщик/роутер выбрал **на этот ход**, всегда видима, даже если
   allowlist роли её не содержит (роль скоупит по работе, роутер выбирает по
   смыслу — при расхождении раньше молча выигрывал allowlist).

2. **Дотянуться было не до чего.** `tool_catalog.ingest_web_source` требовал
   `ToolSupplier.id`, которого у агента в чате взяться неоткуда (пользователь
   и счета оперируют `Party`), и принимал уже извлечённый текст, а не URL.
   *Фикс:* `POST /api/tool-catalog/resolve-supplier` (имя → Party →
   ToolSupplier, с созданием связи как в GUI-пути) и
   `POST /api/tool-catalog/attach-web-catalog` — один вызов «имя поставщика +
   URL»: fetch страницы/PDF (с OCR) → LLM-извлечение позиций → draft-first
   записи в каталоге поставщика. Оба доступны агенту как
   `tool_catalog.resolve_supplier` / `attach_web_catalog`.

3. **План подменял задачу.** В `_plan_turn` любое упоминание имени
   поставщика включало `workspace_required=True` и канвас
   `agent:invoice-items` — «загрузи каталог ООО X» превращалось в «покажи
   товары X». *Фикс:* имя поставщика больше не делает ход табличным, если в
   запросе есть глагол действия (`has_action_intent`, расширен глаголами
   загрузки/прикрепления). Плюс маршрут `supplier_catalog` в `routes.yml`
   (роль `procurement_specialist`) и секция промпта для неё.

4. **Невыполненное действие проходило аудит.** Ход считался успешным, если
   что-то опубликовано на Рабочий стол. *Фикс:* новый `AuditCode.
   ACTION_NOT_PERFORMED` — если пользователь просил действие, а вызовы были
   только читающие/публикующие, ход блокируется, идёт ретрай с явной
   инструкцией, а если и он не помог — агент честно пишет, что действие не
   выполнено, и задаёт **один** уточняющий вопрос вместо подмены отчётом.
   Табличные интенты («обнови таблицу», «отсортируй») из правила исключены.

**Попутная находка (живой прогон нового endpoint'а):**
`_parse_catalog_text_via_llm` обрезал источник до первых 20 000 символов —
на реальном 200 000-символьном PDF-каталоге это обложка, предисловие и
оглавление, и он честно возвращал `rows: []`. Теперь текст парсится чанками
(15k × до 8 чанков, конкурентность 3, дедуп по артикулу+названию), а не
обрезается. Заодно поднят таймаут прокси capability для этих путей: 30s
не хватало на fetch PDF + OCR + LLM-извлечение.

**Тесты:** `backend/tests/ai/test_action_performed_audit.py` (13),
6 новых в `backend/tests/test_web_catalog_ingestion.py` (резолв по имени
с/без «ООО», неоднозначность → 409 с кандидатами, attach по имени → записи
с `review_status=ingested`, пустая JS-страница → честный 422),
2 новых в `backend/tests/ai/test_role_capability_scope.py`.

### №13.1 — доработка по итогам живой проверки: «все каталоги», отчёт со ссылками

После первого фикса агент мог прикрепить **один** каталог по известной ссылке.
Живая проверка на mirstan.ru показала, чего не хватает для реальной задачи
«найди все каталоги поставщика и прикрепи»:

- **Поиск всех каталогов.** `POST /api/tool-catalog/discover-catalogs`
  (`tool_catalog.discover_catalogs`): веб-поиск (`site:<домен> каталог`,
  «<имя> прайс-лист», …) **плюс** обход собственного сайта поставщика со
  сбором ссылок. Второй проход был невозможен: браузер-сайдкар отдавал только
  текст страницы, а «Скачать каталог» — это `<a href>`, которого в тексте нет.
  Добавлены `include_links`/`links` в `infra/web-browser/server.py` и в
  `app/api/web_search.py`. Кандидаты ранжируются: файлы (PDF/Excel) с сайта
  поставщика первыми, страницы — последними. Живая проверка: 18 кандидатов,
  включая 2 PDF-каталога, из них один найден только обходом сайта.
- **Прикрепление всех разом.** `attach_web_catalog` принимает `urls: [...]`
  (до 20) и обрабатывает каждый независимо: битая ссылка возвращается строкой
  `status=error`, JS-страница — `status=empty`, остальные прикрепляются. Если
  не удалось ничего — честный `422`, а не «успех с нулём позиций».
- **Отчёт с кликабельными ссылками.** Ответ несёт готовый блок `report`
  (`columns`/`rows`), где колонка ссылки имеет `type: "link"` — грид
  (`frontend/components/grid/ActionCell.tsx`) рендерит её как `<a target=_blank>`.
  В живой сессии модель сама выбрала `type: "text"`, поэтому ссылки не
  кликались; теперь агенту предписано публиковать `report` как есть.
- **Бюджет извлечения тратится на каталог, а не на обложку.** Чанки текста
  ранжируются по плотности каталожных сигналов (артикул, Ø/мм, цена):
  первые 24 000 символов каталога СКИФ-М — обложка, предисловие и оглавление,
  и «первые N чанков» давали ровно 0 строк, тогда как те же деньги, потраченные
  на плотные страницы, дают сотни позиций (331 строка на прогоне с 16 чанками).
  Чанки парсятся строго последовательно: локальный Ollama обслуживает один
  слот, поэтому «параллельные» чанки лишь выжигали собственный таймаут в
  очереди.

### №13.2 — загрузка каталога уходит в фон; модель разбора берётся из настроек

Живой замер на боевом стенде: разбор одного фрагмента PDF-каталога — около
5 минут (локальная модель, Ollama обслуживает один слот), полный каталог на
200 000 символов — десятки минут. Держать ход чата (и GPU) открытым столько
времени — неверная форма.

- `attach_web_catalog` по умолчанию **ставит загрузку в очередь** (Celery,
  очередь `gpu`) и отвечает сразу: `status=queued`, список источников и
  готовый `report` со статусом «В очереди на загрузку». Синхронный разбор
  остался под явным `wait=true` (им пользуются тесты и осознанный
  «дождись сейчас»).
- Прогресс по каждому источнику пишется в `app/domain/catalog_ingest_status.py`
  (Redis + in-memory fallback): `queued → running → attached|empty|error`.
  Новое действие `tool_catalog.ingest_status` отдаёт его вместе с таким же
  `report` — «как там каталоги?» отвечается фактами, а не пересказом того,
  что агент поставил в очередь минуты назад.
- Модель разбора переключена с reasoning-слота (APEX 35B) на
  `get_verify_model()` — то есть на назначение **STRUCTURED_EXTRACTION** из
  GUI-настроек моделей (сейчас там `qwen3.8:27b-131072`). Смена модели для
  этой задачи теперь решение в интерфейсе, а не правка кода.
- Имена источников в отчёте раскодируются из percent-encoding
  (`%D0%9A%D0%B0%D1%82...` → `Каталог-СКИФ-М-2023.pdf`).

**Живая проверка потока целиком (mirstan.ru):** `discover_catalogs` → 20
кандидатов, из них 4 PDF-каталога (ROXX, INSIZE, Diamitron, СКИФ-М; часть
найдена только обходом сайта) → `attach_web_catalog(urls=[4 файла])` →
мгновенный ответ `queued` + отчёт с кликабельными ссылками → фоновый разбор
в GPU-очереди. Синхронный прогон того же СКИФ-М ранее дал **38 реальных
позиций** в каталоге поставщика (`tool_catalog_entries`), так что цепочка
проверена от ссылки до записи в БД.

**Ещё две находки на живом прогоне фонового пути:**

- Глобальный `task_soft_time_limit=300` (celery_app.py) убивал разбор
  каталога на середине: первый источник успевал (135 позиций реального
  каталога СКИФ-М в БД), остальные навсегда оставались в статусе `queued` —
  неотличимо от «ещё в работе». Задаче даны свои лимиты (soft 1800 / hard
  1860), `SoftTimeLimitExceeded` перехватывается и помечает источник как
  `error` с причиной, а attach ставит **по задаче на каждый источник**, так
  что большой каталог не съедает бюджет остальных.
- **Деплойная заметка:** задачи `drawing_analysis.*` идут в очередь `gpu`, её
  обслуживает `celery-worker-gpu` — при добавлении новой задачи нужно
  пересобрать и его, иначе воркер отвечает `Received unregistered task`
  (поймано на живом прогоне).

## №14 — ложный `filter_missing` и подвисание хода на мёртвых embedding'ах ✅

Живой ход «Покажи счета поставщика ООО Мир Станочника» после починки роутера:
`plan_source=router:model:analytical_table` (эвристика больше не участвует,
решение за 8628 мс при прежнем общем лимите 8000 мс — роутер опаздывал на
полсекунды и каждый ход уходил в эвристику). Но сам ход занял **19 минут** и
не прошёл аудит. Две независимые причины.

**1. Аудит не понимал фильтр внутри spec-таблицы.** План требует
`supplier_query=X`; агент опубликовал корректную таблицу, где фильтр выражен
как `supplier_name contains "Мир Станочника"` **внутри spec**. Проверка искала
ключ `supplier_query` среди аргументов вызова, не находила и выдавала
`filter_missing` → ретрай, который стоил большую часть тех 19 минут.
*Фикс:* `_filter_satisfied_by_spec` — план-фильтр считается выполненным, если
опубликованный spec фильтрует по соответствующей реальной колонке
(`supplier_query` → `supplier_name`/`supplier`/`supplier_inn`), со сравнением
без учёта регистра и организационно-правовой формы («ООО Мир Станочника» ==
«Мир Станочника»). Другой поставщик и нефильтрованная таблица по-прежнему
считаются промахом.

**2. Векторные вызовы наследовали разговорный таймаут провайдера (180 с).**
Ollama обслуживает один слот: пока фоновый разбор каталога занимал его,
каждый `/api/embed` просто стоял в очереди — восемь `ReadTimeout` подряд по
цепочке `qwen3_embedding_8b_ollama` → `local_embedding_ollama`, при простое
GPU. Проверено прямым curl: `/api/tags` — 0.7 мс, `/api/chat` — 0.47 с,
`/api/embed` и `/v1/embeddings` — не отвечают за 25-60 с (в логах Ollama
запись о них не появляется вовсе, запрос висит до обработчика).
*Фикс:* `app/ai/router.py` — `_FAST_TASK_DISPATCH_TIMEOUT` (embedding/reranking:
25 с на кандидата) и `_FAST_TASK_CHAIN_BUDGET` (40 с на всю цепочку, дальше
`ai_route_chain_budget_exhausted`). Разговорные задачи не тронуты: reasoning-
модель законно думает минутами, эмбеддинг — никогда.

**Замечание по железу (не код):** RTX 3090 24 ГБ, из них 21.3 ГБ держит
`qwen3.8:27b-131072`. Свободных ~1.4 ГБ, и при занятом слоте embedding-модель
не может быть обслужена. Пока embedding и reasoning делят один узел Ollama,
RAG-контекст в ходах будет деградировать (быстро и честно — но деградировать).

## №15 — «покажи счета поставщика X» публиковало ВСЕ 152 счёта ✅

Продолжение №14. Повторная живая проверка показала, что `filter_missing` в том
ходе был **верным**: агент передал `filters.supplier_query="ооо мир станочника"`
в `workspace.invoice_table`, но `WorkspaceInvoiceTableRequest` такого поля
никогда не имел (в отличие от items-таблицы) — Pydantic молча его отбросил, и
на Рабочий стол ушли все 152 счёта под заголовком «полный список».

**Фиксы:**
- `WorkspaceInvoiceTableRequest.supplier_query` + фильтрация по `Party.name`
  (тот же ILIKE, что в items-таблице), честный `not_found` для несуществующего
  поставщика (как в находке №5), заголовок и `filters` в ответе отражают
  применённый фильтр. Живая проверка: 3 счёта вместо 152.
- Аудит читает фильтр и во вложенном `filters` (капабилити-вызовы передают его
  и так, и на верхнем уровне), а фильтр по `supplier_id`/`party_id` в spec
  засчитывается как более точный вариант фильтра по имени.

**Урок:** параметр, который принимающая схема не объявляет, исчезает молча —
и виноватым выглядит агент. Стоит держать сигнатуры родственных таблиц
согласованными (invoice_table vs invoice_items_table разошлись именно так).

## №16 — узлы Ollama: GPU и CPU выбираются в настройках ✅

Продолжение №14/№15 (embedding на GPU-узле не отвечал). Причина оказалась не
только в занятом слоте: у хостовой Ollama `OLLAMA_MAX_LOADED_MODELS=1`, то есть
любой запрос к embedding-модели требует выгрузить 27B-reasoning и загрузить
другую — запрос висел даже при **простаивающей** GPU (проверено curl'ом:
`/api/tags` 0.7 мс, `/api/chat` 0.47 с, `/api/embed` — не отвечает за 90 с).

**Решение — отдельный CPU-узел** (`ollama-cpu` в docker-compose): без доступа к
видеокарте (`CUDA_VISIBLE_DEVICES=""`, без device reservation), общий каталог
моделей с хостом (ничего не качается дважды), embedding + reranker резидентно.
Бэкенд многоузловой режим уже умел (`provider_instances`, `select_instance`,
`PATCH /api/providers/models/{key}/preferred-instance`) — не хватало UI и
самого узла. В `/settings/models` у каждой локальной модели появился селектор
«Узел: авто / ollama (default) / ollama-cpu».

**Про железо (замеры этого стенда):** Ryzen 9 9900X (12 ядер Zen 5, AVX-512),
59 ГБ RAM, RTX 3090 24 ГБ, из которых 21.3 ГБ держит 27B-модель. Встроенная
графика Granite Ridge (2 CU RDNA2) для инференса бесполезна: ~1 TFLOPS против
~35 у 3090, та же системная память, и ROCm/Ollama её штатно не поддерживают.
CPU — правильный выбор: **60-100 мс** на эмбеддинг после прогрева.

**Модели (выбор владельца, с одной вынужденной заменой):**
- embedding — `qwen3-embedding:4b` (официальная сборка, 2560 измерений).
  `dengcao/Qwen3-Embedding-4B:Q8_0` НЕ подходит: `ollama show` даёт
  `Capabilities: tools, completion` без `embedding`, поэтому llama-server
  стартует без `--embeddings` и `/api/embed` отвечает 501.
- rerank — `dengcao/Qwen3-Reranker-4B:Q8_0` (работает через `/api/generate`
  с `think:false` + logprobs). Живая проверка: 0.996 / 0.025 / 0.0 на
  релевантном и двух посторонних документах.

**Векторные хранилища при смене модели** — раньше ломались молча:
- `VECTOR_SIZE = 4096` был зашит константой, поэтому фиксированные коллекции
  (`tool_catalog`, `drawings`, `drawing_features`) оставались на старой
  размерности и отвергали каждую запись. Теперь размерность берётся из
  активного профиля; при несовпадении — предупреждение в лог, а по явному
  запросу переиндексации коллекция пересоздаётся.
- Триггеры рецептов и коннекторов оставались в старой коллекции: рецепты
  живы в Postgres, но перестают находиться по сходству — агент молча
  перепланирует то, что уже умеет. Добавлены `recipes.reindex_all_triggers`
  и `connectors.reindex_all_triggers`.
- `POST /api/ai-settings/vector-reindex` — одна операция, которая переводит
  на активную модель всё сразу: документы, каталог, триггеры рецептов и
  коннекторов, с честным перечнем ошибок.

**Живая миграция:** каталог — 1046 записей, 2560 измерений, 0 ошибок (261 с);
память документов переиндексируется тем же путём.
