## 2. Диагноз: семь системных причин

**Д1. Модель данных — «деталь известного класса».** Спек — это набор полей под классы:
`outer/bore/keyways/cross_holes` у вала, `profile.holes/slots` у пластины,
`wall_features` у корпуса, `sheet_metal`, `parts`, `placed_features`… Деталь, которая не
ложится в класс, невыразима. «Опора пружин» — полая втулка с внутренним профилем
(Ø8,5 → Ø5,7 → конус 18° → Ø7,6 → Ø9,8), резьбой, буртом и профрезерованной вилкой — не
выражается ни одним классом целиком.

**Д2. Геометрию просят у модели, а не меряют.** Ридер задаёт модели узкие вопросы под
класс и получает числа в схему. Модель путает внутренние и наружные Ø (у «Опоры» Ø8,5H10
и Ø9,8H10 — отверстия, прочитаны как ступени), виды между собой, выносные элементы с
сечениями. При этом свободным текстом та же модель описывает деталь хорошо (ответы
«Опиши деталь» на z4-r4 верны), но этот канал используется только как мешок чисел.

**Д3. Проверка — 39 частных проверяльщиков с 210 порогами, настроенных на свой
синтетический корпус.** Корпус рисует тот же код, что и эталон; реальные сканы и фото
ломают базовый шаг: на «Опоре» поиск вида вала находит **штамп**, потому что профиль
строится по «самой внешней симметричной паре» и случайная симметрия штампа и соседнего
вида её перебивает.

**Д4. Согласование — правила из конкретных листов.** 50 функций, каждая выросла из
разбора одного живого прогона. Правило для одного листа ломает другой: 2026-09-26 вопрос
о сечениях (для многоосевых валов) сломал сборку z4-r4 — канавки выносных элементов
прочитаны «лысками».

**Д5. Блокеры — свободный текст.** `unresolved` — список строк без предмета и жизненного
цикла. Каждое правило добавляет строки, снять их можно только строковыми шаблонами;
половина блокеров на реальных листах — устаревшие или ни к чему не привязанные.

**Д6. Оценка мерит не то.** Синтетика своего генератора + 7 реальных листов, и гейт
реальных листов не проверяет «собралось ли тело». Храповик держит «не хуже базы», а не
качество (паз на v10 был верен в 15 из 31 при зелёном гейте). Реальные листы
пользователя в оценку не входят вовсе.

**Д7. Нет замкнутого контура «деталь ↔ лист».** Собранное тело сравнивается с листом
только у тел вращения (E11). Чертёж ЕСКД из тела ядро строит, но как проверка не
используется — хотя это и есть цель режима (деталь → 3D → чертёж ЕСКД).

## 3. Целевая архитектура: от видов листа, а не от класса детали

```
лист ─► A. разбор листа: рамка, штамп, ТТ; виды и их роли (главный, разрез, сечение,
        │   выносной, вид по стрелке); масштаб
        ▼
        B. векторизация видов: отрезки, дуги, окружности с типом линии (основная,
        │   тонкая, штриховая, осевая), регионы штриховки — одна процедура для всех
        ▼
        C. размеры как связи: надпись (читает модель по вырезу) ↔ размерная линия ↔
        │   две сущности вида (привязывает код); решатель подгоняет измеренный эскиз
        │   к номиналам; не сошлось — точечный вопрос или человеку
        ▼
        D. 3D по видам — стратегия по доказательствам, не по классу:
        │   • ось симметрии → вращение полупрофиля вида/разреза (наружный И внутренний
        │     контур сразу — «Опора» получила бы расточку даром)
        │   • замкнутый контур плана + толщина по другому виду → выдавливание
        │   • всё остальное — элементы-отличия между видами (отверстие: окружность в
        │     одном виде + канал/штриховые в другом; лыска/фрезеровка: хорда в сечении +
        │     линия в виде) → операции по 3D-размещению (ядро уже умеет, дорожка У)
        ▼
        E. проверка = перепроекция: ядро строит из тела те же виды, разрезы и сечения,
        │   что на листе; сравнение по сущностям: каждая линия листа объяснена телом,
        │   каждая линия тела есть на листе; расхождение локализовано
        ▼
        F. спорное → точечный вопрос по вырезу или оператору с наложением;
           выход — тело + чертёж ЕСКД из тела (ядро уже строит)
```

Роль модели меняется: она **интерпретирует** (какой вид главный, где разрез, что за
элемент, какой текст у надписи, соответствие видов), а не выдаёт геометрию в схему.
Числа — только с надписей, форма — только с линий листа.

Модель детали одна: **эскизы + операции + элементы по 3D-размещению** (шаг У1
`features.py` — начало этого). Нынешний спек по классам становится адаптером для
совместимости и истории.

## 4. Что сохранить, что вывести из работы

**Сохранить (это уже фундамент нового):** ядро (эскизы из отрезков и дуг, вращение,
выдавливание, элементы по 3D-размещению, виды/разрезы/сечения по ЕСКД), построение листа
из тела (`sheet_from_solid`), граф EMG и контракт вердиктов, выпрямление и увеличение
листа (SeedVR2), переспрос по вырезу, журнал событий, поиск мелких сечений и следов
секущих, сравнение проекции (E11) — как зародыш этапа E, генераторы корпусов — как
юнит-страховка.

**Вывести постепенно (в тени, отключение по корпусу):** классовые узкие вопросы ридера
(оставить как подсказки), частные проверяльщики (становятся частными случаями
сопоставления векторов), правила согласования, выведенные из одного листа, блокеры
свободным текстом.

**Убрать сразу:** путь «Python-скрипт профиля» (0 из 99), его переспрос.

## 5. Оценка, которая не даст снова подгонять

- **Эталонный корпус реальных листов с 3D:** 30–50 деталей разных типов (валы, втулки,
  полые, с фрезеровкой, пластины, корпуса, литьё, гнутые, сварные); эталон — модель,
  построенная вручную в редакторе и проверенная оператором. Треть — отложенная часть,
  по ней ничего не настраивается.
- **Главная метрика:** доля листов, где собранное тело совпадает с эталоном (объём
  ±1 %, отклонение поверхности в пределах точности листа), и доля честно отданного
  человеку (не собрано — но с верной причиной). Вторичные — по этапам A–E.
- **Гейт:** ни один лист, который собирался, не перестаёт собираться; абсолютные доли
  видны в отчёте, а не только разность с базой.
- Синтетика — только юнит-страховка, и со вторым, независимым рендером (TechDraw
  напрямую / ezdxf) плюс фото-деградации.

## 7. Решения оператора (2026-09-26)

1. **Корпус** — собрать самому из открытых источников: реальные чертежи совершенно
   разных деталей и сборок; эталонные 3D-модели строятся по ним.
2. **Параллельно**: новый метод `views` рядом со `spec`, потом просто замена.
3. **Частные правила** — пересмотреть поштучно: что полезно в общем виде — перенести в
   новый конвейер, остальное заморозить.
4. **Главная цель**: распознаватель видит чертёж как инженер — читает чертежи и схемы
   как человек — и может просто перечертить деталь (инструмент построения листа из тела
   уже есть).

## 8. Ревизия частных правил (2026-09-26)

Просмотрены все функции согласования (`reconcile.py`, 50) и стадии проверки
(`stage.py`, 49). Большинство правил — частные случаи нескольких общих
принципов; принципы переносятся в метод `views`, частные сборщики спека
замораживаются.

**Переносятся как общие механизмы**

| Принцип | Где сейчас | Куда в `views` |
|---|---|---|
| Замер принимается, только если его объясняет надпись листа; иначе — человеку | `reconcile`, `_plate_hole_position`, `profile_decision`, `placed_additions`, `weldment_placement_decision` | этап C: номинал всегда из надписи, замер выбирает, какая надпись к какой геометрии |
